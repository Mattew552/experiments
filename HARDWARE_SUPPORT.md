# Расширение аппаратной поддержки FanGuardian

Исследование от 29 октября 2026 года для ветки `Test`. Это план реализации по исходникам и документации; он не подтверждает работу перечисленного оборудования на реальном ПК. Аппаратные команды в ходе исследования не выполнялись.

## Практическая цель

FanGuardian может автоматически выбирать подходящий адаптер оборудования и показывать доступные функции: управление, только показания или отсутствие поддержки. Обещание управления абсолютно любым ПК невыполнимо: вентилятор с питанием Molex не имеет программного входа, а часть OEM-систем не предоставляет стороннему ПО интерфейс записи. В Windows стандартный `Win32_Fan.SetSpeed` не реализован; один WMI-вызов не заменит драйверы оборудования. [Microsoft: Win32_Fan](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/win32-fan).

Первоочередная цель — разные настольные Windows-ПК. Ноутбуки подключаются по проверенным моделям, Linux — отдельным backend, macOS — отдельным проектом интеграции. Переписывать приложение на другой язык для этого не требуется.

## Конкретные способы доступа

| Оборудование | Адаптер | Что реализовать | Предел возможностей |
| --- | --- | --- | --- |
| Разъёмы платы через Super I/O | LibreHardwareMonitor + PawnIO | Сохранить основной backend, учитывать модель платы и чип; обновлять проверенные версии LHM и отправлять новые конфигурации плат upstream | Чтение RPM не гарантирует наличие работающего control |
| USB fan controllers и СЖО, уже известные LHM | Отдельные LHM controller adapters | Включать проверенные группы/модели и описывать их возможности, отдельно вентиляторы и помпы | Наличие устройства в LHM не гарантирует управление |
| Corsair Commander, часть NZXT, AquaComputer, Lian Li и других USB-устройств | liquidctl helper или прямой HID backend | Зафиксировать версию и список VID/PID/firmware; получать состояния портов и управлять только разрешёнными fan outputs | Поддержка зависит от конкретной модели и ОС |
| ASUS и другие OEM-интерфейсы | Модельные WMI/ACPI/SDK adapters | Использовать известные методы конкретной модели; проверять, что метод предоставляет именно чтение или независимую запись | Общая смена Silent/Turbo может менять несколько подсистем одновременно |
| Ноутбуки | Модельный EC/vendor backend, профиль NBFC как источник сведений | Точное совпадение модели и прошивки, известные регистры и процедура возврата; CPU-only endpoints | Нельзя применять профиль похожей модели или сканировать неизвестные EC-регистры записью |
| Linux | hwmon/sysfs или CoolerControl REST API | Сначала адаптер к готовому daemon; затем собственный привилегированный hwmon service при необходимости | Драйвер ядра должен предоставлять writable PWM/auto интерфейс |
| Плата без доступного программного управления | Поддерживаемый USB PWM-контроллер | Подключить обычные совместимые вентиляторы к известному контроллеру, независимо от Super I/O платы | Это аппаратное изменение; SATA-разветвитель без USB-интерфейса не добавляет программное управление |

Источники для реализации:

- [LHM Computer.cs](https://github.com/LibreHardwareMonitor/LibreHardwareMonitor/blob/master/LibreHardwareMonitorLib/Hardware/Computer.cs): группы AquaComputer, NZXT, Arctic, Razer, MSI, AeroCool и другие включаются через `IsControllerEnabled`.
- [LHM SuperIOHardware.cs](https://github.com/LibreHardwareMonitor/LibreHardwareMonitor/blob/master/LibreHardwareMonitorLib/Hardware/Motherboard/SuperIOHardware.cs): конфигурации чипов и плат.
- [liquidctl: устройства и API](https://github.com/liquidctl/liquidctl#supported-devices), [Commander Core](https://github.com/liquidctl/liquidctl/blob/main/docs/corsair-commander-core-guide.md), [Commander Pro](https://github.com/liquidctl/liquidctl/blob/main/docs/corsair-commander-guide.md). У этих Commander документирована индикация подключения портов; это конкретный способ узнать наличие подключения без вывода только по изменению RPM.
- [OpenFanController](https://github.com/SasaKaranovic/OpenFanController): пример внешнего USB-контроллера с описанным API.
- [ASUS WMI plugin](https://github.com/Mourdraug/FanControl.AsusWMI): дополнительный путь чтения датчиков, а не универсальная запись скорости.
- [NBFC](https://github.com/hirschmann/nbfc), [NBFC-Linux FAQ](https://github.com/nbfc-linux/nbfc-linux/wiki/FAQ), [G-Helper](https://github.com/seerge/g-helper/blob/main/docs/README.md): модельные способы доступа ноутбуков.
- [Linux hwmon ABI](https://docs.kernel.org/hwmon/sysfs-interface.html), [CoolerControl](https://github.com/codifryed/coolercontrol): RPM, PWM, режимы управления и daemon API. Атрибуты hwmon опциональны, поэтому каждый канал требует проверки возможностей.

FanControl использует LHM и отдельные плагины; само приложение имеет закрытый исходный код. Это пример работающей архитектуры, а не готовая открытая универсальная библиотека для встраивания. Можно отдельно исследовать host для совместимых плагинов, но каждый плагин требует аудита функций и условий использования. [Совместимость FanControl](https://github.com/Rem0o/FanControl.Releases/blob/master/README.md), [Plugin API](https://github.com/Rem0o/FanControl.Releases/wiki/Plugins).

## Что сейчас ограничивает наш код

1. `Hardware.cs`: `IsControllerEnabled=false`, регистрация controls только для `HardwareType.SuperIO`.
2. `Hardware.cs`, `FanProbe.cs`, `MainForm.cs`: префикс `/lpc/` используется как разрешение записи. Для USB и OEM нужен типизированный источник и список возможностей.
3. `Model.cs`, `Engine.cs`: только роли `Cpu`, `FrontTop`, `FrontPair`; остановка требует ровно две передние группы. Нужен произвольный список групп с отдельными названиями и ролями.
4. `IFanHardware.Default()` не описывает семантику возврата. В [LHM KrakenV3.cs](https://github.com/LibreHardwareMonitor/LibreHardwareMonitor/blob/master/LibreHardwareMonitorLib/Hardware/Controller/Nzxt/KrakenV3.cs) default задаёт фиксированные скорости помпы/вентиляторов; это не восстановление прежнего режима. В [Octo.cs](https://github.com/LibreHardwareMonitor/LibreHardwareMonitor/blob/master/LibreHardwareMonitorLib/Hardware/Controller/AquaComputer/Octo.cs) есть показания, но нет управляющих `IControl`.
5. `WorkerHardware.cs`: UI и сторож имеют отдельные LHM-экземпляры. Для новых backend лучше передать все чтения и записи одному владельцу устройства, чтобы не было конфликтующих HID-сеансов и разных снимков состояния.
6. `MachineIdentity.cs`: привязка учитывает установку Windows, но не изменение платы или контроллера при сохранении этой установки.
7. `FanProbe.cs`: два среза RPM, ожидание три секунды и пауза полторы секунды не проверяют стабилизацию, повторяемость и восстановление. Сравниваются даже датчики других контроллеров. Пороги 250–10000 RPM и 20–65 °C — ограничения текущего прототипа, а не универсальные свойства вентиляторов.

## Контракт адаптера оборудования

Выделить `FanGuardian.Core` без WinForms, реестра и конкретных драйверов. Существующий UI остаётся Windows-клиентом. Каждый `IHardwareBackend` обнаруживает устройства и возвращает описание каналов:

| Поле | Назначение |
| --- | --- |
| Backend / DeviceId / ChannelId | Устойчивый адрес устройства и выхода, без догадок по строковому префиксу |
| Origin / Role | Плата, внешний контроллер, CPU fan, case fan, pump, GPU или unknown; роль пользователя хранится отдельно от подсказки firmware |
| ReadRpm / SetDuty / SetRpm / HardwareCurve | Независимые возможности; одно не подразумевает другое |
| ConnectionDetection | `Explicit`, `Inferred`, `Unknown`; реальный признак контроллера отдельно от результата пробы |
| DutyRange / RpmRange / KnownMinimum | Границы конкретного канала, включая медленные и серверные вентиляторы |
| RestoreStrategy | `RestoreOriginal`, `FirmwareAuto`, `SafeFallback`, `None`; фиксированный fallback не подписывается как BIOS |
| ControlDomain / SharedEffects | Какие выходы затрагивает команда, независим ли канал |
| ProbePolicy / Watchdog | Допустимые шаги, длительность, способ аварийного возврата |
| Version / Firmware | Версия backend и прошивка, для которых канал проверен |

Сервис выбирает одного владельца записи для каждого устройства: LHM и liquidctl не управляют одним HID одновременно. Плагины запускаются изолированно, их capabilities не считаются доказанными только по наличию метода `Set`.

Запрет команд GPU проверяется в привилегированном процессе по происхождению устройства и области действия команды. Глобальные OEM-команды, которые могут изменить CPU и GPU fans вместе, запрещены. Например, [Dell hwmon](https://docs.kernel.org/hwmon/dell-smm-hwmon.html) на некоторых моделях имеет общий переключатель автоматического управления; его нельзя выдавать за независимый CPU-канал.

## Автоматическое подключение системы

1. Пассивное обнаружение: ОС, модель/ревизия платы, контроллеры, версии драйверов, температура CPU, RPM и явные состояния USB-портов. Нет управляющего интерфейса — показывать причину, а не пустой экран.
2. Известный профиль платы или USB-протокол предлагает соответствие выходов. Название `CPU_FAN` — подсказка разъёма, но оно не доказывает, что пользователь действительно подключил туда CPU-кулер.
3. Для неизвестной пары собрать несколько baseline-образцов до устойчивого RPM. Сравнивать тахометры того же устройства/контроллера, учитывать пропуски и разброс.
4. Одному разрешённому каналу задать безопасное увеличение. Ждать стабилизации с общим тайм-аутом, а не фиксированные три секунды. Использовать монотонный `Stopwatch`, чтобы перевод системных часов не продлевал пробу. Измерение, ограничение длительности и восстановление выполняет worker; UI только отображает процесс. Не снижать неизвестный CPU/pump output ради обнаружения.
5. Вернуть исходный режим, проверить обратную реакцию и стабильность. Повторить опыт; сохранять кандидата только при повторяемом отклике и отсутствии сопоставимого дрейфа остальных каналов.
6. Исходные 100%, постоянная скорость, отсутствие тахосигнала, несколько изменившихся RPM или неуспешный возврат дают `Unresolved`, а не «пустой разъём». Для помп и общих выходов нужен отдельный профиль.
7. Пользователь подтверждает только то, что программа не видит: CPU/корпус/помпа и физическая группа. Разветвитель остаётся одной группой управления; число крыльчаток не выводится из одного RPM.
8. Сохранить привязку к локальному отпечатку платы/контроллера и версии прошивки/backend. Исходные серийные номера не помещать в публичные логи или репозиторий. При смене оборудования или проводки требуется повторная проверка.

Вместо одного признака «канал проверен» хранить независимые свидетельства: активный тахометр, наблюдаемая связь, повторённая связь, проверенный возврат, подтверждённая роль, рабочий ненулевой диапазон, проверенная остановка. Готовые пары, сообщённые протоколом, сокращают число испытаний: например, [Plugin API FanControl](https://github.com/Rem0o/FanControl.Releases/wiki/Plugins) предусматривает `PairedFanSensorId`.

Примеры существующих сценариев — [Assisted Setup FanControl](https://github.com/Rem0o/FanControl.i18n/blob/main/AssistedSetup/AssistedSetup.json), [калибровка CoolerControl](https://docs.coolercontrol.org/cooling/calibration), [Auto-Create CoolerControl](https://docs.coolercontrol.org/cooling/auto-create). Они отделяют электрическое сопоставление от назначения CPU/корпус/помпа. [pwmconfig](https://github.com/lm-sensors/lm-sensors/blob/master/prog/pwm/pwmconfig) также учитывает время раскрутки и проверяет возврат RPM; копировать его остановочные пробы на неизвестные каналы не следует.

## Порядок реализации и критерии готовности

| Этап | Конкретная работа | Критерий завершения |
| --- | --- | --- |
| 1. Общая модель | Backend/capabilities, произвольное число групп, привязка к плате/контроллеру, явная семантика восстановления | Проверенный MSI-сценарий сохранён; неизвестные и GPU-выходы не получают обычные команды |
| 2. Надёжный мастер | Несколько образцов, стабилизация, локальное сопоставление, возврат и повторная проба | На стенде подтверждены успешное сопоставление, неоднозначность, отмена, зависание UI и потеря связи |
| 3. Широкая Windows desktop поддержка | Проверенные семейства Nuvoton/ITE и каталог моделей плат поверх LHM | Для каждой записи каталога опубликованы версия и фактически проверенные чтение/запись/возврат |
| 4. USB | Первый конкретный адаптер с явным присутствием портов, например Commander Core/Pro через liquidctl; затем другие модели | Независимое управление портами, исключение GPU/помп, отключение USB и безопасный возврат проверены на реальном устройстве |
| 5. Ноутбуки/OEM | Только точные профили моделей и CPU-only endpoints | Проверены прошивка, отсутствие воздействия на GPU и возврат штатному контроллеру |
| 6. Другие ОС | Linux hwmon/CoolerControl adapter; отдельный клиент UI при реальной потребности | Сервис и firmware корректно переживают закрытие клиента/перезапуск; это отдельная аппаратная матрица |

Автотесты должны покрывать сохранённые обезличенные снимки разных чипов, дубликаты/пропуски датчиков, старт с 0 RPM, исходные 100%, общий control, дрейф температуры, ошибку записи и невосстановленный режим. Они проверяют логику, но не заменяют реальные устройства. Статусы поддержки вести раздельно: найден по документации, реализован, проверен чтением, проверен управлением, проверен возврат.

Перед распространением перенести проект с .NET 9 на .NET 10 LTS и подготовить самодостаточную Windows x64-сборку: поддержка .NET 9 заканчивается 10 ноября 2026 года. ARM64 требует отдельной проверки backend/драйверов, даже если UI/runtime запускаются. [Политика .NET](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core), [поддерживаемые Windows/архитектуры](https://learn.microsoft.com/en-us/dotnet/core/install/windows).

Зависимости и плагины подключать после проверки их собственных лицензий и вести `THIRD-PARTY-NOTICES`: [LHM](https://github.com/LibreHardwareMonitor/LibreHardwareMonitor), [PawnIO](https://github.com/namazso/PawnIO#license), [PawnIO modules](https://github.com/namazso/PawnIO.Modules), [liquidctl](https://github.com/liquidctl/liquidctl). Отдельный helper-процесс сам по себе не заменяет проверку условий распространения.
